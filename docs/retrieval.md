# Retrieval architecture

Extend parses documents into source text, pages, and layout blocks. Text formats are decoded locally. The index records heading structure, sections that continue across pages, page ranges, links, and exact block references. Markdown code fences do not create headings. Long sections become overlapping 2,400-character source passages; passage selection never depends on matching query words.

Indexing does not call a chat model or generate summaries. It stores structural descriptions from heading outlines and page ranges, alongside the original source text. Chat providers generate conversational answers and, separately, occasional folder names and descriptions for [automatic filing](organization.md).

The two JEV references solve different problems. Hierarchical classification traverses a supplied tree using Choice distributions; it does not generate that tree. GPT Researcher's context filter scores raw passages from pages already found by web search, then supplies accepted passages to a writer. That filtering stage does not require document summaries or a persistent hierarchical index. This library uses its accessible document tree for candidate selection and the same usefulness-scoring principle for evidence filtering. Without generated summaries, heading quality limits how informative document and section routing descriptions can be.

At query time the backend constructs the caller's accessible hierarchy down to sections. Reaching a section supplies its original passages to the context filter directly; a second routing decision cannot discard passages before they are scored. Attached documents constrain that hierarchy. Category descriptors use category metadata; document outlines and source text are never copied into a shared category descriptor. All reads use SpiceDB permissions.

Automatic filing changes the folder portion of this hierarchy. After parsing, JEV classifies an incoming document against existing folders using headings and bounded original-text samples. It may descend through existing subfolders or request a new branch whose names and descriptions come from a separately selected model. JEV validates that branch before it is created. This does not replace the document's parsed section and subsection structure, and it does not generate document summaries.

Upload-driven organization reviews reuse this hierarchy to shortlist related older documents. This lookup preserves category branches even when constrained to eligible document IDs, scores at most 24 passages, and returns at most eight passages. It keeps conservative routing: branches rejected by none are excluded rather than recovered. Only those shortlisted documents can receive full placement classification; JEV compares their current and proposed paths before moving. Normal chat retrieval and attached-document behavior keep their existing budgets and scoping.

JEV Choice evaluates sibling menus. Each frontier batches up to four independent routing questions, with a 24,000-character menu budget per request. Menus have at most 16 children plus a none option. Larger menus gain intermediate routing groups; category routes remain directly visible when they fit alongside grouped documents. The backend never compares probabilities from unrelated flat batches. Permissions are checked again before each request. Descriptions are partial outlines: a none probability at least as large as a child defers that route rather than permanently excluding its contents.

The beam retains four routes by `exp(sum(log(edge_probability)) / decision_count)`. Single-child transitions do not count as decisions. A probability floor of 0.000001 permits bounded exploration of routes assigned zero probability. Traversal yields candidate sections before continuing deeper, allowing evidence quality to guide further exploration. Deferred routes remain available for another pass when fewer than three useful passages are found. Exploration is capped at 96 node expansions and 96 passage scores per query.

JEV Score then evaluates candidate source passages independently on a four-level usefulness rubric, following GPT Researcher's separation of candidate collection and context filtering. Scores below 1.5 are excluded. Scoring has a process-wide concurrency limit of sixteen, with live authorization checks inside the limiter. Results are ordered by usefulness, then route score, and limited to twelve passages and 24,000 characters. A routing score ranks a path; it is not a calibrated probability that a passage answers the question. Empty results remain empty, and invalid or unavailable providers fail explicitly.

Retrieval paths include per-edge probabilities, normalized route scores, and scored passage visits. Citations identify the original document, section, passage, page range, and source blocks. The chat model answers from these passages and may make another bounded search when evidence is insufficient. Search tool instructions ask for self-contained queries that include relevant topics and document references from prior conversation turns.

This implementation uses TypeSafe as the decision provider and does not require PageIndex, its cloud service, a vector store, or a keyword index. PageIndex's separation of document structure and source reads informs the design; its runtime is not integrated.

References: [TypeSafe hierarchical classification](https://docs.typesafe.ai/cookbooks/hierarchical_classification), [JEV context filtering](https://docs.gptr.dev/docs/gpt-researcher/gptr/context-filter), and [PageIndex document trees](https://docs.pageindex.ai/sdk/documents).
