# Security boundaries

## Authorization

Every authenticated resource lookup is scoped to the session's organization, with a live membership check. Client-supplied organization IDs are never used to scope resource access. Authorization covers listings, original bytes, parsed content, indexing status, edits, downloads, search results, routing prompts, citations, and conversations.

SpiceDB is mandatory: there is no SQL-only authorization fallback. Checks use full consistency and the organization’s committed graph version. A PostgreSQL transaction serializes mutations, writes a fresh relationship snapshot, and publishes its version only after every SpiceDB write succeeds. Partial writes remain unreachable; failed updates roll back and preserve the previously committed permissions. Errors return 503 rather than treating the unavailable service as an allow. Superseded snapshots are removed after a grace period. Do not edit membership or grant tables outside the application.

Startup rebuilds every organization's relationship snapshot from PostgreSQL before serving requests, repairing missing or stale SpiceDB relationships after a restore or service reset. Each resource has a structural parent (or organization root); only resources with inherited access also have an inheritance relation. Moving a folder changes that branch's parent and inheritance relations in the new snapshot, so all inherited descendants immediately follow the destination's permissions. Moving an inherited resource to the workspace root makes it private. Deletion removes the subtree from the committed graph. Renaming changes metadata without changing permissions.

Resources start private. Owners can manage sharing and delete; explicit editors can edit; viewers can read. Organization access grants read access only. Inherited access follows the parent. For authenticated workspace access, every ancestor is an upper bound: a direct user grant on a child never bypasses a private category. Explicit public links have a separate view-only permission rooted at the shared resource. Organization administrators configure integrations and members; they do not automatically gain access to private documents owned by other members.

Better Auth owns signup, sign-in, sign-out, email verification, password recovery, sessions, and organization invitations. The frontend uses its client and organization plugin; registration policy and organization provisioning run through its supported hooks. Better Auth enforces origin checks for its endpoints. Application mutations retain their separate request-origin checks.

Invitations use Better Auth's single-use IDs, expire after seven days, and are bound to an email. Treat invitation IDs and links as secrets. Better Auth sends the invitation email and requires mailbox verification before password sign-in or invitation acceptance. Verification creates a session, and the application resumes native invitation acceptance with the matching verified account before opening the organization. New accounts cannot join by guessing an email or organization ID. SSO and MFA are not enabled.

Production signup is disabled unless `ALLOW_SIGNUP=true`. The first account can be created with `BOOTSTRAP_TOKEN`; after an account exists, further users require invitations. Treat the bootstrap token as a deployment secret. Local development permits separate organization registration.

## Chat and retrieval

JEV ranks only resources visible to the caller. Search traverses nested category → document → section candidates with parallel sibling questions and length-normalized path scores. Alternative routes are explored when the first beam provides too little useful evidence. Retrieved source passages receive independent usefulness scores; routing probabilities are not evidence confidence. Retrieval is bounded and returns at most twelve passages within a 24,000-character context budget; it is not an exhaustive proof that no other relevant source exists. A TypeSafe key is required. Provider failures never fall back to unfiltered content, keyword matching, or embeddings.

Indexing preserves page and block references and stores structural outlines without calling chat providers. Document outlines and passage text are checked under that document's permission; they are not copied into shared category descriptions. Chat models generate conversational answers and occasional generic folder definitions for automatic filing. Large sibling sets form intermediate routing groups whose descriptions are rebuilt from currently accessible children. Permissions are rechecked before routing, before and after passage scoring, and before returning results and paths.

Automatic filing acts as the uploader and only moves still-private documents without explicit grants. Candidates must be writable by that user and lie within the selected upload folder. Permission, source, placement, and folder metadata checks run before each provider call and again inside the commit transaction. Manual placement cancels the pending job; changed sharing or revoked access stops filing without changing the document index. New root folders are private; nested folders inherit their parent's access, while the document retains private access. Generated folder definitions can therefore be visible to readers of the parent. The prompt prohibits private document-specific facts and JEV checks the proposed definitions, but model judgments are fallible. Full placement distributions are kept server-side and are not exposed in resource metadata. See [automatic filing](organization.md).

Conversations are bound to a user and organization. They record the union of every source and category dependency, including sources used in earlier turns. Every read and continuation checks that dependency set again; any revoked or deleted source blocks the whole conversation, including its title and earlier user messages. Authorization is checked again after retrieval and generation, before persistence or response. There is no cross-user prompt or result cache. Already downloaded content cannot be recalled from a user who previously had access.

Uploads can trigger bounded related-document reviews through the existing permission-filtered retrieval index. Candidate metadata is restricted to the uploader's still-private documents previously filed automatically, excluding manual placements and explicit grants. Full reclassification is limited to the returned shortlist and retains the original upload scope. Permissions and placement are checked again before queueing and before committing a move. Reviews do not create folders or recursively trigger more reviews.

Provider keys are organization-scoped and encrypted with AES-256-GCM. They are write-only through the UI; responses return configuration flags. The selected provider receives only authorized excerpts and that user's still-authorized history. Provider errors are sanitized rather than reflecting response bodies, credentials, or prompts to clients. A document's instructions are treated as untrusted source material. Generated answers remain fallible and should be verified against citations.

## Browser and network

Better Auth manages email/password authentication and signed HttpOnly, SameSite=Strict session cookies, with Secure on HTTPS. Sessions expire after one day, have no cookie cache, and are checked against live organization membership and SpiceDB on every application request. Password reset revokes all sessions; users can also sign out other devices. Application mutations require the configured origin and an explicit application header. Native authentication endpoints use Better Auth’s origin and CSRF checks. All API content is private/no-store. Passwords use Better Auth’s native hashing; imported hashes upgrade through its credential adapter after a successful sign-in. Authentication rate limits use Better Auth’s native PostgreSQL storage and trusted client IP buckets. API limits remain in process, and this remains a single-replica application. Trusted client IPs come from Express proxy handling rather than user-supplied forwarding headers.

Original content is served only after authenticated resource checks or public-link permission checks, with nosniff and a sandbox CSP. Active/unknown file types are served as attachments. Markdown does not execute HTML and blocks remote images. HTML previews are sanitized and run in an iframe with an empty sandbox and restrictive CSP. SVGs are sanitized and loaded as images. Code is displayed with Pierre Diffs and is never executed. Archive previews are bounded to 1,000 entries, 5 MB per entry, and 20 MB expanded; text previews cap rendering length. Unknown formats are never executed.

Custom provider endpoints require public HTTPS and reject redirects. DNS is resolved and validated at connection time; private, loopback, link-local, multicast, and mapped private IP ranges are blocked. Provider options cannot load credential files from the server. Cloud adapters require explicit organization credentials rather than application host identities. Community extensions are code installed by the deployment operator, never arbitrary module imports supplied by a organization member.

## Operations

Background work uses private PostgreSQL queues. Workers recheck live membership and resource permissions before provider requests and result publication. Queue payloads contain resource identifiers; authentication email links, recipients, and queued chat session credentials are encrypted. Tokens and provider credentials are not included in queue errors. An active-attempt fence prevents cancelled or expired workers from publishing stale results. Keep queue administration restricted to deployment operators. See [background jobs](jobs.md) for retry and external-effect limits. Production runs one web process with separately scalable workers; the single-web-replica limit does not prevent multiple queue consumers.

The encryption key and BETTER_AUTH_SECRET must survive restarts and be backed up separately from data. The auth secret signs session cookies and verification links; rotating it invalidates outstanding cookies and links. Kubernetes takes it from an existing Secret. Local development generates a mode-0600 key in the data directory. Production stores original files and thumbnails in a private S3 bucket, with metadata and object references in PostgreSQL. Local development and unmigrated legacy files can still contain database bytes. Stored S3 bytes are checked against their recorded size and SHA-256 on reads; original and thumbnail routes recheck authorization before responding. S3 credentials stay server-side. Encrypt both PostgreSQL databases and their backups at rest, and use verified TLS for database connections in deployed environments. SpiceDB must have a dedicated datastore; the application installs its permission schema at startup.

The Helm chart runs non-root with a read-only root filesystem, dropped capabilities, no Kubernetes API service-account token, optional projected AWS identity tokens for IRSA, and network policies for application ingress, private SpiceDB access, explicitly configured PostgreSQL endpoint ranges, DNS, and public HTTPS. SpiceDB has no public Service or Ingress. Your CNI must enforce NetworkPolicy. Restrict cluster administration and access to snapshots/secrets. Back up both databases, the object bucket, and the key; test restoration. The app audit log records administrative actions, resource changes, sharing, and uploads without document contents or secrets.

Public links are opt-in and view-only. An owner can enable a random bearer link for a document or folder. The server stores a token hash for lookup and an encrypted token for the owner to copy. Each metadata and content request checks the link permission in SpiceDB; folder links reach only descendants that inherit access. Private descendants and unrelated resources are excluded. Disabling link access revokes the token, and re-enabling creates a new one. Public routes expose no edit, share, search, or chat endpoints. Public buckets, remote URL imports, arbitrary provider tools, and shared chats are not enabled. SSO, MFA, malware scanning, retention policies, automatic backups, and multi-replica operation are future operational extensions rather than implied features.

Organization roles are exactly admin and member. Admins manage membership, role assignments, and provider configuration; at least one admin must remain. Administrative status never overrides a document or category restriction. Resource ownership remains separate from organization roles.

## Authentication migration

The Better Auth migration retains user IDs, organization memberships, and documents, imports credential hashes, and invalidates all legacy sessions. New passwords use Better Auth's native hashing. A compatibility verifier accepts previous credential formats and upgrades them on successful sign-in. Existing accounts must verify their email before signing in. The production service requires a stable BETTER_AUTH_SECRET and SMTP configuration; email verification cannot be disabled by omitting email credentials. Verification and recovery links expire after one hour. Mailpit is the development inbox, and production SMTP requires verified TLS. AUTH_LOCAL_DEVELOPMENT is only accepted for loopback origins and is set by the local Compose app; it is not set by the deployment chart.

## Native authentication integration

The browser uses Better Auth’s clients for organization membership, invitations, API keys, and OAuth consent management. The authorization server is the Better Auth MCP/OAuth provider. It issues opaque access tokens, and protected APIs use the provider’s live token validation and DPoP binding utilities. Disconnecting a client deletes its access and refresh tokens through the native adapter in the same transaction as native consent deletion. There is no separate JWT verifier, revocation table, or authentication throttle implementation. Application hooks enforce signup admission, verified accounts, read-only key permissions, administrative safeguards, auditing, and SpiceDB synchronization. Email transport and post-login navigation remain application integrations.

The native-auth migration replaces the old rate-limit storage and revocation table. Previously issued JWT access tokens require reconnection. Interrupted chat work using the old session identifier format requires an explicit retry. Legacy password compatibility is temporary: hashes upgrade at successful sign-in; it cannot be removed until those credentials have migrated or been reset.
